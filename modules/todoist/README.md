# TodoistCompanion module

Action.php owns page-save synchronization, completion/status AJAX, and the local task registry. Syntax.php renders `{{todoistcompanion>Task|id=abcd1234}}` and `~~TODOS~~`. Admin.php owns connection configuration and renders the same live Todoist project list as `~~TODOS~~`. script.js and style.css own the task UI and toolbar dialog.

Credentials resolve from `/run/secrets/todoist_api_token`, then `TODOIST_API_TOKEN`, then `todoist_api_token` under Butler configuration. Runtime state uses `<metadir>/fokusbutler/todoist`. AJAX endpoints use the `fokusbutler_todoist_` prefix. Disabling the module stops synchronization and leaves task text readable.

This is an internal Fokus Butler module, not a separately installable DokuWiki plugin. See [the companion README](../../README.md) for installation, module switches, asset loading, and development checks.

## Todoist project list

`~~TODOS~~` displays every task in the configured Todoist project (default: **Wiki**), including completed tasks retained in local history. The list no longer scans wiki pages for task syntax, so removing `{{todoistcompanion>...}}` from a page does not remove that task from the aggregate. Add an idea to the Wiki project from any Todoist client; the list refreshes while open. Entries show their description as plain text, due date/time and timezone when supplied, recurrence, deadline, labels, creation date, and a linked Todoist logo. Wiki-created tasks also link back to their source page when its task registry entry and read permission are available, with the page's first heading as the link name and its normal DokuWiki preview. Due and added timestamps sit below the task name in the secondary text color at 60% opacity as `YY-MM-DD HH:MM`; date-only due dates omit the time. Explicit timestamp offsets are converted to the task timezone for due dates, or the server timezone for added dates. Priority is hidden. Markdown in descriptions remains readable source text.

Reads use Todoist's [API v1](https://developer.todoist.com/api/v1/) with project filtering and cursor pagination. The wiki renders first, then loads the project list through AJAX so Todoist response time does not delay the page refresh. The server keeps an `incoming.json` snapshot for current tasks, a `completion.json` state cache, and a durable `history.json` archive for completed tasks under the module's metadata directory. It refreshes at most every 20 seconds while the wiki list is open; failed or partial refreshes retain the last successful snapshot and archive. A successful snapshot removes deleted or moved uncompleted tasks from the list while completed task history remains visible. Opening a list never creates a project. Completion from Todoist is reflected as checked, and reopening an active task clears its archived completed state. Open wiki pages poll task status and refresh the list every 20 seconds while visible. Task state checks are cached for 20 seconds.

Todoist project contents require a logged-in user with read access to a page containing `~~TODOS~~`; administrators can also view the list in the TodoistCompanion settings panel. All such readers share the configured account's Wiki project; put the list on an appropriately restricted page in a multi-user wiki. Anonymous readers cannot see project tasks. Parser caching is disabled for task lists. Edit permission on the list page plus a valid CSRF token allows completing an active task in Todoist; administrators can complete from the settings panel. The task's current project and active status are checked again before completion; recurring tasks refresh on the next view. Project tasks do not alter page source or become wiki task syntax. Title/description editing remains in Todoist.

Run isolated Todoist project and archive checks with `php tests/todoist.php`; these use mocked API responses and temporary metadata only.
